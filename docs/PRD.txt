======================================================================
0. EXECUTIVE SUMMARY
======================================================================

Horoi is a privacy-preserving ownership-claim layer for Zcash Shielded Assets
(ZSAs).

A shielded asset can hide who owns it and how much they hold. That privacy
creates a composability problem: applications cannot simply read a public token
balance to decide whether a holder is eligible for a vote, reward, gated action,
or snapshot-based campaign.

Horoi lets a holder prove a statement such as:

    "I held at least 100 units of Asset X at snapshot H"

without revealing:

    - wallet address;
    - exact balance;
    - private notes;
    - unrelated transaction history;
    - past or future spends.

Horoi is NOT:

    - a launchpad;
    - an exchange;
    - a stock market;
    - a bridge;
    - a generic wallet;
    - a generic ZSA registry;
    - an EVM smart-contract application.

The product contribution is a reusable ZSA-specific ownership claim primitive
plus a minimal demo application.

Primary thesis:

    PRIVATE ASSETS NEED PRIVATE COMPOSABILITY.

Long thesis:

    Shielded assets solve confidential ownership, but private ownership is not
    useful to applications unless ownership can be consumed without unshielding
    it. Horoi lets applications verify ZSA ownership conditions without learning
    the holder's exact balance, address, or note history.

Hackathon one-liner:

    Horoi lets applications verify ZSA ownership without revealing the owner.

======================================================================
1. WHY THIS EXISTS
======================================================================

1.1 Current problem

Public-token applications commonly implement holder logic like this:

    address
      -> read public balance at block H
      -> compare balance >= threshold
      -> allow vote / reward / access

That pattern is incompatible with the privacy goal of ZSAs because the useful
ownership state is shielded.

Naive workarounds are unacceptable:

    - reveal exact balance;
    - reveal wallet address;
    - reveal private notes;
    - reveal a viewing key;
    - maintain a centralized ownership database.

Those approaches weaken or destroy the privacy property.

1.2 Zcash-specific gap

The Zcash draft:

    "Air drops, Proof-of-Balance, and Stake-weighted Polling"

defines a proof-of-balance direction for Orchard ZEC and explicitly says:

    "Claim refers to a proof by a ZEC holder (TODO: support ZSAs)..."

Horoi targets that exact missing ZSA-specific application primitive.

1.3 Problems Horoi solves

Horoi must provide:

    1. immutable snapshot-bound claims;
    2. AssetId-bound ownership statements;
    3. balance-threshold proofs;
    4. local witness construction;
    5. local zero-knowledge proving;
    6. domain-separated alternate nullifiers;
    7. public proof verification;
    8. note-level replay protection inside a claim domain;
    9. an application-facing API;
   10. a minimal frontend demonstrating the complete flow.

4. PRODUCT PRINCIPLES
======================================================================

P1. Privacy first

Private wallet state remains client-side.

P2. One cryptographic implementation

Rust is the single source of truth for ZSA claim cryptography.

TypeScript must never reimplement:

    - AssetId validation math;
    - note commitment logic;
    - alternate-nullifier derivation;
    - claim-domain field encoding;
    - claim proof verification.

P3. Testnet honesty

ZSA remains experimental/testnet-grade.

P4. Minimal code surface

Do not create many tiny helpers, wrappers, services, repositories, or utility
files when one cohesive domain file is clearer.

P5. Fail closed

Unknown or inconsistent cryptographic state must reject.

P6. Immutable public statement

After creation, a claim's cryptographic statement cannot change.

P7. Explicit protocol version

All proof bundles are versioned.

P8. Minimal persistent data

The backend stores only public claim metadata and replay-prevention data.

======================================================================
5. MVP USER FLOWS
======================================================================

5.1 Create Claim

A creator enters:

    name
    description
    AssetId
    minimum balance
    snapshot height
    optional expiration

Backend:

    - validates input;
    - resolves snapshot data;
    - creates immutable claim metadata;
    - creates a claim-specific domain;
    - stores the claim.

5.2 Generate Proof

A holder opens a claim.

Browser:

    - loads claim public data;
    - loads local prover WASM;
    - obtains public ZSA chain data;
    - scans/decrypts the holder's local testnet ZSA state;
    - selects one eligible normal note;
    - builds its witness locally;
    - creates alternate nullifiers;
    - creates proof locally.

No wallet secret is sent to the backend.

5.3 Verify Proof

Any verifier can verify a proof bundle against the immutable claim.

Response:

    VALID
    or
    INVALID

5.4 Submit Claim

A holder submits the HCP1 proof bundle and its public alternate-nullifier
encoding. HCP1 carries the nine circuit public fields; the API binds them to the
stored claim instead of accepting a separate publicInputs object.

Backend performs an atomic flow:

    1. load claim;
    2. reject expired claim;
    3. parse HCP1 public fields and bind them to stored claim metadata;
    4. cryptographically verify proof;
    5. compare the submitted alternate nullifier with the verified proof output;
    6. reject a reused nullifier;
    7. store the accepted nullifier;
    8. return accepted result.

======================================================================
6. NULLIFIER SEMANTICS — IMPORTANT
======================================================================

Horoi MVP provides NOTE-LEVEL replay protection.

Correct statement:

    "The same contributing note cannot be reused in the same claim domain after
    its alternate nullifier has been accepted."

Incorrect statement:

    "The same person can only claim once."

Incorrect statement:

    "The same wallet can only claim once."

Why:

A holder may have multiple separate eligible note sets. Alternate nullifiers
prevent reuse of the same note in one claim domain, but they are not a universal
human identity or wallet identity primitive.

Horoi is not an anti-Sybil protocol.

UI copy must say:

    "These notes have already been used in this claim."

Do not say:

    "This user already claimed."

unless a future protocol version actually proves that property.

======================================================================
7. CLAIM PROTOCOL
======================================================================

7.1 Public claim data

Every claim contains:

    protocolVersion
    networkId
    claimId
    name
    description
    assetId
    threshold
    snapshotHeight
    commitmentRoot
    exclusionRoot
    claimDomain
    expiresAt

7.2 Private witness

A holder's witness may contain:

    one normal note's data, value, and randomness
    spend-authority material required by the proof construction
    commitment paths
    nullifier non-membership witnesses
    local wallet state

These values must never be sent to Horoi backend.

7.3 Statement

The prover must establish that:

    - the note belongs to assetId;
    - the note existed at snapshotHeight;
    - the note was unspent at snapshotHeight;
    - the prover has the required authority;
    - the note value is >= threshold;
    - the note maps to an alternate nullifier under claimDomain.

7.4 Exact balance

Exact note value must remain private.

Only threshold satisfaction is public.

7.5 Asset binding

The circuit/proof MUST bind the note to the public AssetId.

A proof for Asset A cannot be accepted for Asset B.

7.6 Snapshot binding

Proof verification MUST bind:

    networkId
    snapshotHeight
    commitmentRoot
    exclusionRoot

A claim cannot silently move to a newer snapshot.

7.7 Integer values only

Asset values are integer units.

HTTP values use decimal strings.

Example:

    "100"

Never use JavaScript floating point for ZSA amounts.

7.8 Maximum notes

Initial target:

    MAX_NOTES = 4

Current implementation supports one normal note only. Four-note aggregation is
an unimplemented target, not a current MVP capability.

If profiling shows the proof is too slow, reduce the bound and document it.

Do not pretend multi-note support exists if only one-note support is implemented.

7.9 Claim domain

Claim domain must be deterministic and domain-separated.

Logical input:

    "horoi-claim-v1"
    networkId
    claimId

Exact byte encoding and field conversion live in Rust only.

7.10 Claim ID

Claim ID must be deterministic and versioned.

Recommended logical preimage:

    protocolVersion
    networkId
    assetId
    threshold
    snapshotHeight
    commitmentRoot
    exclusionRoot
    expiresAt
    creatorNonce

Canonical serialization and hashing are owned by Rust.

7.11 Protocol version

MVP:

    protocolVersion = 1

Any breaking change to:

    proof format
    circuit statement
    public-input encoding
    nullifier encoding
    domain construction

requires a protocol version bump.

8. SMART CONTRACT DECISION
======================================================================

Horoi does NOT use a Solidity smart contract.

Reason:

The target Zcash ZSA/Orchard environment is not an EVM application environment.
Adding Solidity purely to have a "smart contract" would be architecturally
incorrect.

Use these simple names instead:

    ClaimCircuit
    ClaimProof
    ClaimVerifier

They are Rust/ZK components, not Solidity contracts.

Forbidden unless this PRD is explicitly revised:

    contracts/
    *.sol
    Foundry
    Hardhat

Cross-chain verifier contracts are out of MVP scope.

Do not persist full submitted proofs by default.

14. API
======================================================================

Base:

    /api/v1

14.1 GET /health

Response:

    {
      "ok": true,
      "version": "1.0.0",
      "network": "zsa-testnet"
    }

14.2 GET /claims

Public claim list.

Optional query:

    limit
    cursor
    status = active | expired

Status is computed from expiry at query time. Apply status filtering before
descending-ID cursor pagination. Unsupported status values return BAD_REQUEST.

14.3 GET /claims/:id

Returns canonical public claim data.

14.4 POST /claims

Request:

    {
      "name": "ACME Holder Test",
      "description": "Prove at least 100 ACME at the selected snapshot.",
      "assetId": "...",
      "threshold": "100",
      "snapshotHeight": 12345,
      "expiresAt": null
    }

Backend:

    validate
      -> verify AssetId encoding
      -> verify snapshot exists
      -> resolve roots
      -> create nonce
      -> call Rust canonical claim builder
      -> persist immutable claim

14.5 POST /proofs/verify

Stateless proof verification.

Request:

    {
      "claimId": "...",
      "protocolVersion": 1,
      "proof": "...base64 HCP1 bundle...",
      "alternateNullifiers": ["...one 32-byte field encoding..."]
    }

HCP1 carries nine circuit public fields. The verifier reconstructs the expected
statement from the stored claim and cryptographically verifies those embedded
fields. The API request has no separate publicInputs object.

Valid response:

    {
      "valid": true,
      "claimId": "...",
      "alternateNullifier": "...",
      "statement": {
        "assetId": "...",
        "threshold": "100",
        "snapshotHeight": 12345,
        "protocolVersion": 1
      }
    }

This endpoint does not consume nullifiers.

14.6 POST /claims/:id/submit

State-changing submission.

Request:

    {
      "claimId": "...",
      "protocolVersion": 1,
      "proof": "...base64 HCP1 bundle...",
      "alternateNullifiers": ["...one 32-byte field encoding..."]
    }

The path claim ID must equal claimId. HCP1 carries the nine circuit public
fields; the verifier checks them against the stored claim statement. The API
checks the submitted alternate nullifier against the value derived by the
verified proof. No separate publicInputs object is sent.

Atomic sequence:

    load claim
      -> reject expired
      -> parse HCP1 public statement and bind it to the stored claim
      -> verify proof cryptographically
      -> check the proof-derived alternate nullifier against the submitted value
      -> check whether the nullifier is already consumed
      -> insert nullifiers
      -> commit

Two concurrent submissions with the same nullifier cannot both succeed.

Do not create tests for trivial:

    rendering
    getters
    static strings
    route wrappers
    schema passthrough

20.2 The one automated test file

Keep one Rust integration test file:

    backend/rust/tests/claim.rs

This file covers only cryptographic/protocol invariants that cannot be safely
validated by clicking through a browser.

Required cases:

    valid threshold proof verifies
    insufficient value does not produce/verify an eligible proof
    wrong AssetId fails
    wrong snapshot/root fails
    modified public input fails
    same note + same domain derives same alternate nullifier
    same note + different domain derives different alternate nullifier
    invalid witness fails
    proof serialization round trip

If multi-note proving is implemented:

    aggregation >= threshold succeeds
    aggregation < threshold fails

No extra Rust test file unless there is a distinct cryptographic subsystem that
cannot reasonably fit in claim.rs.

20.3 Static validation

Backend:

    bun install --frozen-lockfile
    bun check
    bun run build or equivalent compile validation

Frontend:

    bun install --frozen-lockfile
    bun check
    bun run build

Rust:

    cargo fmt --check
    cargo check --locked
    cargo test --locked --test claim

Do not add a large lint/tool chain only for the hackathon.

20.4 Browser testing

Frontend and end-to-end behavior must be tested through the ChatGPT browser,
not through a new browser automation test suite.

Preferred process:

    1. run the app or expose a preview URL;
    2. open it using ChatGPT Browser / connected browser;
    3. exercise the actual UI;
    4. inspect browser/runtime errors;
    5. fix implementation;
    6. repeat until the acceptance flow passes.

Browser smoke flow:

    /
      -> hero renders
      -> Browse Claims works

    /create
      -> invalid AssetId shows documented error
      -> valid test claim can be created

    /claims
      -> new claim appears

    /claims/:id
      -> metadata matches created claim
      -> proof UI initializes
      -> no wallet secret is sent in network requests

    Generate Proof
      -> local prover loads
      -> proof generated for eligible test wallet

    Submit Claim
      -> valid proof accepted

    Repeat same contributing notes
      -> NULLIFIER_USED

    /verify
      -> accepted proof verifies
      -> tampered proof returns INVALID

20.5 Browser privacy inspection

During browser testing, inspect network requests.

The following must never appear in request payloads:

    seed phrase
    spend key
    viewing key
    exact private balance
    decrypted private note data

20.6 No test theatre

Do not create fake tests merely to increase test count.

For Horoi:

    cryptographic invariants -> automated Rust test
    UI/E2E behavior          -> ChatGPT Browser
    TypeScript correctness   -> bun check + build

That is the intended validation strategy.

22. CODE QUALITY RULES
======================================================================

22.1 Naming

Names must describe what the code does.

Good:

    createClaim
    getClaim
    verifyProof
    submitClaim
    getSnapshot
    ClaimCircuit
    ClaimVerifier

Avoid:

    manager
    engine
    orchestrator
    handlerFactory
    gatewayService
    processor
    coordinator

unless that word is truly the domain concept.

22.2 Functions

Prefer small, readable functions.

Do not split a five-line function into a separate helper file.

22.3 Comments

Comment:

    cryptographic assumptions
    protocol constraints
    non-obvious security behavior
    ZSA compatibility workarounds

Do not comment obvious syntax.

22.4 Errors

Do not repeat the same error text throughout the code.

Use stable error codes and central HTTP mapping.

22.5 TypeScript

Use:

    strict TypeScript
    unknown for untrusted exceptions/input where appropriate
    Zod at HTTP boundaries
    explicit result handling for expected failures

Avoid:

    any
    non-null assertions without proof
    unsafe JSON casts
    floating-point token values

22.6 Rust

Use:

    stable Rust
    checked conversions
    explicit error enums
    zeroization where applicable for secret material
    no unwrap/expect on untrusted runtime input
    constant-time primitives provided by upstream cryptographic libraries

Do not roll custom cryptography.

22.7 No dead code

Do not keep:

    unused routes
    future placeholder modules
    commented-out implementations
    duplicate schemas
    unused packages

27. DEMO SCRIPT

Demo asset:

    ACME
    Illustrative label only. Do not associate it with the recorded public
    testnet AssetId unless that mapping is verified. Clearly label any local
    demo as "Demo ZSA. No real-world security claim."

State:

    The Alice/Bob threshold example is illustrative only; it is not evidence
    of two distinct public-testnet holders.

Recorded public-testnet demo (2026-10-25): one genuine eligible note met
threshold 100 at snapshot 7596 and produced a valid browser HCP1 proof. A
separate u64::MAX insufficient-balance test returned NoEligibleNote for the
same test-wallet note data; it did not demonstrate Bob or a second holder.

For a live demo, use only a currently eligible, authorized testnet note and
verify the active QEDIT testnet identity before creating a claim. Do not issue,
transfer, burn, or fund assets just to reproduce the demonstration. If no
eligible public note is available, present the recorded evidence and label it
as historical; never label a fixture as a public-testnet result.

Demonstrated one-note flow:

    Open claim
      -> Generate Proof
      -> browser proves locally
      -> Submit
      -> ACCEPTED
      -> stateless verification is valid
      -> identical note replay is rejected in the same claim domain
      -> tampered proof is invalid

Show privacy:

    exact balance = hidden
    wallet = hidden
    notes = hidden

The public E2E report records one accepted eligible note and a distinct-domain
nullifier check. It does not establish a second holder, person-level uniqueness,
or multi-note aggregation.

Do not fake chain state in the final hackathon demo if the submission claims a
real ZSA testnet integration.

Recommended short description:

    Horoi lets applications verify that a holder met a ZSA balance condition at

    address, or private transaction history.

Recommended thesis:

    Private assets need private composability.

    Shielding ownership should not force applications to choose between privacy
    and utility.

    Horoi binds a ZSA AssetId, balance threshold, and snapshot into a
    zero-knowledge claim, then uses claim-domain alternate nullifiers for
    note-level replay protection.
